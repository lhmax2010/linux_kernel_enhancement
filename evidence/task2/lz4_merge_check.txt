    lib/lz4: Allow the fast decode loop on armv7
    
    The in-kernel LZ4 decompressor picks LZ4_FAST_DEC_LOOP the way upstream
    v1.10.0 does, i.e. on x86/x86_64 and on arm64 with a non-clang compiler.
    armv7 is not on that list, so on ARCH=arm the whole fast loop is compiled
    out even though it measures faster there.
    
    The fast loop copies a fixed 32 bytes per sequence instead of taking an
    unpredictable branch, and only engages while at least
    FASTLOOP_SAFE_DISTANCE (64) bytes of output space remain, so the overwrite
    is always in bounds.
    
    Add CONFIG_LZ4_DECOMPRESS_FAST_LOOP as an additional way to select it,
    defaulting to y on armv7 (CPU_V7) unless the kernel is size-optimised.
    The existing architecture tests are left in front of it, so x86 and arm64
    keep using the fast loop unconditionally and nothing changes for them.
    
    This only affects the LZ4_decompress_safe*() family, which goes through
    LZ4_decompress_generic() and is what erofs, squashfs, f2fs, zram, the
    crypto API and initramfs decompression use. LZ4_decompress_fast() has its
    own LZ4_decompress_unsafe_generic() implementation since the v1.10.0
    rebase, so lib/decompress_unlz4.c, used for self-decompressing kernel
    images, is unaffected.
    
    Measured on armv7-a (gcc 13.3.0 -O2 -march=armv7-a), decoding a 5.6 MB
    kernel-source payload split into independent LZ4 blocks:
    
      chunk    CONFIG=n     CONFIG=y
      4 KiB    732 MB/s     779 (+6.4%)
      64 KiB   644 MB/s     687 (+6.1%)
    
    .text of lib/lz4/lz4_decompress.o in a tizen_bcm2711_defconfig build:
    
      CONFIG=n     10344
      CONFIG=y     18260 (+7916, +77%)
    
    That is why size-optimised builds are excluded. With the option off the
    generated code is unchanged, so builds that do not opt in are unaffected.
