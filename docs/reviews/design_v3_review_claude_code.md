### §1.2 指标与分母

**R1.2-1【重要】“全机物理占用 = 物理内存总量 − 空闲页”在有内存压力的场景下测不出变化，在没有压力的场景下又会被页缓存污染**

- 位置：1.2 表格“全机物理占用”一行。
- 问题：
  1. 标准场景包含“后台积累、内存压力”。在有压力的场景里，空闲页会一直贴着水位线，“总量 − 空闲”接近一个常数。任何节省都会被页缓存或更多存活的应用吃掉，表现为“占用不变”。所以这个指标对压力场景无效。
  2. 在没有压力的场景里，它包含可回收的文件缓存。一个减轻了内存压力的改动，可能因为留下更多页缓存而显示为“占用增加”，被误判为回退。
  3. 4.4 已经要求评估“同等内存预算下的容量”，但 1.2 没有把容量指标写成门槛。
- 依据：
  - MemFree 计入所有区的空闲页，包括空闲的 CMA 页；
  - 页缓存可以回收，它的多少由回收策略和历史决定，与方案本身的驻留成本无关；
  - 任务 5 的静置快照中 PSI 为 0，说明静置状态不代表压力场景（09 F 节）。
- 修改方案：

  原文：

  > | 全机物理占用 | 标准场景结束时和场景峰值的物理占用 = 固定的物理内存总量 − 空闲物理页；分列内核保留页、文件缓存、匿名页、slab、zram 成本 | 同一场景、同一存活应用集合下的基线值 | 比值的单侧 95% 置信上界 ≤ 1.03 |

  新文字：

  > | 全机不可回收占用（无压力场景） | 内核保留页 + SUnreclaim + KernelStack + PageTables + 驻留匿名页 + Shmem + Unevictable + zram 物理成本（3.4.3）；文件缓存和可回收 slab 单列，只用于解释 | 同一场景、同一存活应用集合下的基线值 | 比值的单侧 95% 置信上界 ≤ 1.03 |
  > | 内存容量（压力场景） | 固定的应用轮换脚本下，后台存活应用数、pswpout 与匿名 refault 次数、resourced 和内核的查杀次数 | 同上 | 存活数的比值下界 ≥ 0.97；pswpout、refault、查杀次数的比值上界 ≤ 1.03 |

  另外在口径说明中加一句：“无压力场景的定义是 PSI memory 的 some.avg10 始终为 0，且场景期间 pgscan 的增量为 0。”
- 需要增加的测试：在阶段 0b 用两个“已知扰动”校验这两个指标：一是常驻分配 16 MiB 的匿名内存，应当使不可回收占用上升；二是只增加文件缓存，不可回收占用应当不变。

**R1.2-2【重要】在 ARM32 上，kretprobe 拿不到页分配的 GFP 标志和阶数；现有的 tracepoint 已经能直接给出**

- 位置：1.2 表格“非 CMA 低端内存”一行，“用 kretprobe 统计页分配失败，记录 GFP 标志和阶数”。
- 问题：
  1. 在返回探针里读取函数入口参数（`$argN`）需要 `CONFIG_HAVE_FUNCTION_ARG_ACCESS_API`（`kernel/trace/trace_probe.c:780,985`）。只有 x86 和 arm64 等架构选择了它（`arch/x86/Kconfig:278`、`arch/arm64/Kconfig:239`），ARM32 没有选。而在返回点上，`%r0` 已经是返回值，不再是 gfp。
  2. 实际上不需要 kprobe：`__alloc_pages_noprof()` 在 `out:` 处**无论成功还是失败**都会调用 `trace_mm_page_alloc()`（`mm/page_alloc.c:4877-4884`），失败时 `pfn` 字段为 `-1UL`（`include/trace/events/kmem.h:192`），事件中同时带有 `gfp_flags` 和 `order`。
  3. 大量分配失败属于正常行为，例如带 `__GFP_NORETRY` 或 `__GFP_NOWARN` 的试探性高阶分配、zsmalloc 第一次不带直接回收的尝试。直接用“失败次数不增加”作门槛，会把这些良性失败也算进去。
- 修改方案：
  - 原文：“低端内存页分配失败次数（用 kretprobe 统计页分配失败，记录 GFP 标志和阶数）”
  - 新文字：“低端内存页分配失败次数：在 tracefs 中启用 `kmem/mm_page_alloc`，加过滤条件 `pfn == 4294967295`（32 位下的 -1UL），记录 gfp_flags、order 和 migratetype；判定只统计不带 `__GFP_NORETRY`、`__GFP_NOWARN`，且 order ≤ 3（PAGE_ALLOC_COSTLY_ORDER）、最高可用区 ≤ NORMAL 的失败，其余单列报告”
- 副作用：这个 tracepoint 打开后，每次页分配都要执行一次过滤判断。开销需要先用 A/A 测出来，只在诊断轮次中打开，不在验收轮次中常开。
- 需要增加的测试：用一个带 `__GFP_NORETRY` 的 order-4 分配压力，确认它被分到“单列”一类；在 lowmem_reserve 极大的条件下制造一次 GFP_KERNEL 的 order-0 失败，确认被计入。

### §1.3 统计判定

**R1.3-1【重要】多个指标同时要求通过时，中性变体的整体通过率很低，按现有轮次几乎不可能证明“不回退”**

- 位置：1.3“样本量”“判定”。
- 问题：
  - v3 要求每个关键场景、每类必验指标都单独达到单侧 95% 的非劣效。这是“全部通过才算通过”的合取检验。每个终点都按 80% 检出力设计时，k 个独立终点全部通过的概率约为 0.8^k：k=10 时约 11%，k=20 时约 1%。也就是说，一个真正中性的变体，大概率会被判为“无法证明不回退”。
  - n ≈ 12.4·(CV/δ)² 只对应单个终点 80% 的检出力。
- 修改方案：在“样本量”末尾追加：
  > 每个变体在实验计划中预登记必验终点数 k。整体检出力目标为 80%，每个终点的检出力取 0.8^(1/k)（k=10 时约 97.8%，对应 z≈2.0），此时每组轮次约为 n ≈ 2(1.645 + z)²(CV/δ)²（k=10 时约 26.6·(CV/δ)²，大约是单终点的两倍）。终点太多、导致轮次超出板时间预算时，把部分终点降为“安全监测”（点估计不超过容差、并且没有显著回退即可），在计划中写明。
- 需要增加的测试：在判定程序的模拟检查中加入“10 个终点都无真实差异”的情形，统计整体通过率，确认与设计值一致。

**R1.3-2【重要】用 `cycles / cpu-clock` 算出来的不是频率**

- 位置：1.3“频率”：“每轮用 `perf stat -a -e cycles,cpu-clock` 计算有效频率……有效频率低于锁定值 98% 的轮次作废重跑”。
- 问题：
  - 系统级的 `cpu-clock` 按墙钟计时，包含空闲时间；而 Cortex-A72 进入 WFI 时时钟门控，周期计数器不再增加。本配置 CPU_IDLE 未启用，但空闲时仍然执行 WFI。
  - 所以两者的比值是“利用率 × 频率”，不是频率。没有跑满 CPU 的场景轮次会被大量误判为降频而作废。
- 修改方案：
  - 原文：“所以每轮用 `perf stat -a -e cycles,cpu-clock` 计算有效频率，并读取 `thermal_zone0/temp`；”
  - 新文字：“所以每轮开始和结束时，在每个 CPU 上各跑一次约 100 ms 的绑核纯计算校准循环，用 `perf stat -e cycles,task-clock` 计算这段时间内的有效频率，并读取 `thermal_zone0/temp`；”
- 需要增加的测试：在空闲 90% 的场景中确认校准结果约等于锁定频率；人为加热或降频时，确认校准值下降。

**R1.3-3【一般】合并后的事件数太少时，p99 没有意义**

- 位置：1.3“p99 的计算”。
- 问题：合并所有轮次之后，如果事件总数只有约 300 个，p99 只由最大的 3 个值决定，用 bootstrap 求极端分位数的置信区间也不可靠。
- 修改方案：在该条末尾追加：“p99 只在合并后事件数 ≥ 1000（超过 p99 的事件不少于 10 个）时作为判定指标；不满足时改用 p90，并在计划中预登记。”

### §2 现状基线

**R2.3-1【一般】SWIOTLB 池的位置可以从源码确定；还漏了“存储 I/O 是否经过回弹缓冲”这一风险**

- 位置：2.3 表格 SWIOTLB 一行；3.3.4。
- 依据与问题：
  - 池由 `memblock_alloc_low()` 分配（`kernel/dma/swiotlb.c:334`），**位于低端内存**；高水位统计在 `:968-977`，通过 debugfs 的 `io_tlb_used_hiwater` 读出。
  - RAM 分两段：`00000000-3b3fffff` 和 `40000000-fbffffff`（`temp/task5/A_iomem_config_search.txt:4,7`）。如果存储或 USB 控制器的 DMA 地址范围小于物理内存，HighMem 中页缓存的 I/O 就要经过 SWIOTLB 回弹（多一次 CPU 拷贝）。这时 SWIOTLB 就处在 I/O 热路径上：缩小池子有阻塞 I/O 的风险，回弹拷贝本身也是性能成本。各控制器的 DMA 范围，无法核实。
- 修改方案：
  - 2.3 表中 SWIOTLB 一行的说明改为：“池通过 `memblock_alloc_low` 分配，位于低端内存（`kernel/dma/swiotlb.c:334`）；使用高水位见 debugfs 的 `io_tlb_used_hiwater`；是否有存储 I/O 经过回弹待测”。
  - 3.3.4“方案”前加一句：“先在 tracefs 中启用 `swiotlb/swiotlb_bounced`，统计标准场景中按设备分类的回弹次数和字节数。如果存储 I/O 有大量回弹，就把它作为性能问题单独立项，不缩池。”

- 问题：同一节后文已经写明，外置 BTF 能满足 CO-RE。第 1 项却仍然写着“仍然需要内核 BTF”。
- 修改方案：
  - 原文：“只要还做 CO-RE 字段重定位，就仍然需要内核 BTF；”
  - 新文字：“只要还做 CO-RE 字段重定位，就仍然需要一份与运行内核完全一致的 vmlinux BTF（可以来自内核，也可以来自文件，见下文替代路径）；”

**R3.2-2【重要】“模块化只在模块不加载时节省常驻内存”对本平台的低端内存不成立：模块加载后，代码在 HighMem**

- 位置：3.2 表格后的第一段。
- 依据：
  - ARM 的模块内存由 execmem 以 `GFP_KERNEL | __GFP_NOWARN` 调用 `__vmalloc_node_range()` 分配（`mm/execmem.c:21-31`，范围是 `arch/arm/mm/init.c:507-519` 中的 MODULES_VADDR 区）；
  - `__vmalloc_area_node()` 对不带 GFP_DMA 的请求会自动加上 `__GFP_HIGHMEM`（`mm/vmalloc.c:3651-3652`）；
  - 内建代码则位于内核映像中，占用低端内存。
- 结论：内建代码改为模块后，即使开机就加载，它的代码和数据也从低端内存移到了 HighMem，**低端内存收益依然成立**，全机物理占用大致不变（还会多出页取整和模块元数据的开销）。代价是 4 KiB 页映射带来的 iTLB 压力，以及开机时加载模块的时间。
- 修改方案：
  - 原文：“模块化只在模块不加载时节省常驻内存；加载后可能还多出对齐和管理开销。”
  - 新文字：“模块化在模块不加载时节省全机常驻内存。即使模块被加载，本平台的模块内存经 vmalloc 来自 HighMem（mm/execmem.c:21–31、mm/vmalloc.c:3651–3652），所以低端内存的收益依然存在，全机占用略有增加（页取整和模块元数据）；热点代码改为模块会因 4 KiB 页映射增加 iTLB 缺失，开机加载会增加开机时间，按 1.4 测量。”
- 需要增加的测试：
  - 模块加载后，用 `/proc/vmallocinfo` 中该模块的条目，以及 `/proc/kpageflags` 或 page-types，确认它的物理页位于 HighMem；
  - 比较非 CMA 低端内存的空闲量、开机时间和该子系统的性能。

### §3.3 低端内存（第 8 节问题 2）

**R3.3.1-1【一般】漏了 kswapd 平衡判断的副作用**

- 位置：3.3.1“风险”。
- 依据：kswapd 只要**任意一个**符合条件的区达到高水位就认为节点已平衡；判断时使用不含 CMA 的空闲量，并加上 lowmem_reserve（`mm/vmscan.c:6695-6706`）。提高 reserve 后，DMA 区更难达到平衡，HighMem 紧张时 kswapd 会运行得更久。
- 修改方案：在“风险”末尾追加：“kswapd 的平衡判断以任一区达标为准，并计入 lowmem_reserve（vmscan.c:6695–6706），所以提高 reserve 可能延长 kswapd 的运行时间，需要单独测量 kswapd CPU 和 pgscan_kswapd。”

**R3.3.2-1【一般】vmalloc= 的可调范围受 RAM 第一段的上界限制**

- 位置：3.3.2“依据”“方案”。
- 依据：
  - 低端内存只能来自第一段 RAM，即 `0x00000000-0x3b3fffff`（948 MiB，`temp/task5/A_iomem_config_search.txt:4`），所以低端内存最多能从 768 MiB 增加到 948 MiB，即最多多 180 MiB。
  - 对应的 vmalloc 大小约为 `0xff800000 − 0xC0000000 − 948 MiB − 8 MiB` = 60 MiB，这显然太小。
  - `vmalloc=128M` 时低端内存为 880 MiB，在第一段 RAM 之内，计算成立。
- 修改方案：在“方案”末尾追加：“低端内存的上界不能超过第一段 RAM 的末尾（948 MiB，/proc/iomem），所以本方法最多多出约 180 MiB；实际取值以 vmallocinfo 峰值的两倍为下限。另外，低端内存变大会使 min_free_kbytes 和水位自动重算，报告前后值。”

**R3.3.5-1【一般】SLUB 的 cache 合并会让“按 cache 调整”影响其他 cache**

- 位置：3.3.5“方案”。
- 依据：平台配置 `SLAB_MERGE_DEFAULT=y`，参数相同的 cache 会合并成一个，多个名字共用同一个实际 cache（在 `/sys/kernel/slab/` 下表现为指向同一目录的链接）。这时调整 `cpu_partial` 或 `min_partial` 会作用于整个合并组；要单独调整，需要启动参数 `slab_nomerge`，而它不在常规授权内，本身还会增加 slab 内存。
- 修改方案：在“方案”末尾追加：“调整前先用 `/sys/kernel/slab/` 下的链接关系确认合并组，按合并组报告收益；不在本轮使用 `slab_nomerge`。”

### §3.6.1 异步归还（第 8 节问题 5）

**R3.6.1-1【一般】协议还缺 CPU 隔离，以及与冻结的先后顺序**

- 位置：3.6.1“方案”。
- 问题：
  1. 应用转入后台的时刻，通常就是另一个应用冷启动或切到前台的时刻。此时归还工作（malloc_trim、.NET GC 压缩）会与前台抢 CPU，在 4 核上可能直接拉长首帧时间。
  2. 平台配置 CGROUP_FREEZER=y。如果 resourced 会冻结后台应用（本次证据中的 resourced 配置没有冻结相关的段，无法核实），通知必须在冻结之前完成，否则应用收不到通知，也执行不了归还。
- 修改方案：在“方案”末尾追加：“归还工作放在后台 cpu cgroup 中低权重执行，并推迟到前台应用首帧完成之后开始；如果 resourced 对后台应用使用冻结，顺序固定为‘通知 → 等待回报或截止时间 → 冻结’。测试前台冷启动与后台归还同时发生的情形。”

### §3.7 采样驱动优化（第 8 节问题 4）

**R3.7-1【重要】function profiler 覆盖不了开机过程，“开机时执行过的函数不进入冷函数候选”无法满足**

- 位置：1.4 表格“冷代码按体积优化”一行，以及 3.7 第 3 点。
- 问题：function profiler 只能在开机之后通过 tracefs 的 `function_profile_enabled` 打开，没有对应的启动参数，所以开机阶段（initcall 之后的驱动探测、首次挂载、systemd 早期）调用过的函数不会被计数。3.7 的做法会把这类“开机时只执行一次”的函数当成冷函数，正是 1.4 自己列出的风险。
- 修改方案：
  - 1.4 中原文：“function profiler 的训练必须包含开机过程，开机时执行过的函数不进入冷函数候选”
  - 新文字：“function profiler 无法覆盖开机阶段，所以冷函数候选要再减去‘开机期间执行过的函数’。这个集合由 C2 的首次执行位图训练内核获得；在 C2 实现之前，排除所有带 probe、init、mount、setup 字样的非 `__init` 函数和驱动的 probe 路径，作为保守替代。”
  - 3.7 第 3 点相应补充一句。
- 需要增加的测试：选一个只在开机时调用的非 `__init` 函数（例如某个驱动的 probe 函数），确认它不在冷函数清单中。

### §4.3 换入延迟

**R4.3-1【一般】两个函数放在同一个过滤器里、并且 depth=1，会漏掉嵌套调用**

- 位置：4.3“单次调用耗时”。
- 问题：`do_swap_page` 和 `swap_read_folio` 同时写入 `set_ftrace_filter`，并且 `max_graph_depth=1` 时，在 `do_swap_page` 内部调用的 `swap_read_folio` 位于第 2 层，不会被记录；记录下来的只有缺页路径之外的调用（例如预读），结果有偏差。
- 修改方案：
  - 原文：“用 `set_ftrace_filter` 只给 `do_swap_page`、`swap_read_folio` 插桩，并设 `max_graph_depth=1`”
  - 新文字：“分两轮测量：每轮的 `set_ftrace_filter` 只写一个函数（`do_swap_page` 或 `swap_read_folio`），并设 `max_graph_depth=1`”

### §4.6 开机时间（第 8 节问题 0）

**R4.6-1【重要】按本镜像的启动参数，串口上没有“内核第一条日志”可以用作分段标记**

- 位置：4.6“测量方法”第 2 条。
- 依据：
  - 实际的启动参数（`evidence/task5/A_identity_memory.txt:10`）是 `console=ttyS0,115200n8 earlycon=uart8250,mmio32,0xfe215040 loglevel=4`。`loglevel=4` 时，只有级别小于 4（emerg 到 err）的消息才会输出到控制台，earlycon 也遵循同样的级别。所以正常开机时，串口上不会出现 INFO 级别的内核日志，包括“Booting Linux”和“Run /sbin/init”。
  - zImage 解压器自身的输出需要 `CONFIG_DEBUG_LL`，平台配置中它未设置。
  - 修改启动参数不在常规授权之内。
  - 引导加载器是否会打印读取耗时（例如 U-Boot 的“bytes read in N ms”），无法核实。
- 修改方案：

  原文：

  > 在宿主机上给串口输出逐行打时间戳，以引导加载器开始读取和内核第一条日志（本镜像已配置 earlycon）为界，得到“读取 + 解压”段。

  新文字：

  > 本镜像的启动参数为 `loglevel=4`，串口上没有 INFO 级别的内核日志，不能用“内核第一条日志”作为分段标记。按以下顺序选择方法：
  > ① 串口上能看到的引导加载器自身输出（若打印读取耗时，直接采用）；
  > ② ARM 通用定时器计数器作为统一的时间轴：它从 SoC 上电起计数（54 MHz）。开机完成时，由同一个用户态进程依次读取 CNTVCT（需确认内核开放了用户态访问）和 CLOCK_MONOTONIC，两者之差约等于“固件 + 引导加载器 + 读取 + 解压 + 内核计时开始之前的初始化”；
  > ③ 以上都不可用时，在内核变体中统一加入一个测量补丁，在 start_kernel 开头以 KERN_ERR 级别输出一次计数器值（所有变体，包括基线，都带这个补丁）。
  > 内核初始化段和用户态段，用 dmesg 时间戳和 systemd-analyze。

- 需要增加的测试：
  - 先只读核对串口日志中现有的标记；
  - 在板上验证用户态能否读取 CNTVCT。这需要推送一个很小的测试程序，不在常规授权的“perf 及其依赖”范围内，需要 PM 授权；
  - 连续 10 次冷启动，检查计数器差值的方差。

### §5 实验计划（第 8 节问题 6）

**R5-1【一般】阶段 0a 和 0b 之间有循环依赖**

- 问题：0a 要求在“标准场景下”采集 zoneinfo、vmallocinfo、slabinfo 和非 CMA 低端内存的低谷，而标准场景脚本到 0b 才固化。
- 修改方案：0a 只保留静置状态和不依赖场景的只读采集（Hardware 行、Zone ranges、swappiness、oom_score_adj、btrfs 的 udev 规则、SWIOTLB 位置、能否打开 function profiler、低内存事件）；把所有“标准场景下”的采集移到 0b 中场景脚本完成之后，并作为阶段 1 和阶段 2 的前提。

### §7 后续研发储备（第 8 节问题 6）

**R7.8-1【重要】ARM32 不能按页释放或修改线性映射区中的只读数据，BTF 只能放进 init 区**

- 位置：7.8“设计”。
- 依据：
  - ARM 的 `change_memory_common()` 只允许修改模块区和 vmalloc 区的页属性，其他地址一律返回 -EINVAL（`arch/arm/mm/pageattr.c:66-68`），所以无法把内核映像中只读区里的 BTF 页改为可写再释放。
  - `.BTF` 现在位于 `RO_DATA` 中（`arch/arm/kernel/vmlinux.lds.S:72`），在 `__init_begin`（`:90`）之前。
  - 唯一能在运行时整体释放的映像区域是 init 区（`__init_begin` 到 `__init_end`），它由 free_initmem 释放，释放前会被设为可写。
- 修改方案：
  - 原文：“把原 BTF 放在初始化后可以释放的区域；”
  - 新文字：“修改 ARM 的链接脚本，把 `.BTF` 移进 init 区（`__init_begin` 与 `__init_end` 之间），在 free_initmem 之前（例如 late_initcall）把它复制到 vmalloc；ARM 的 set_memory_* 只支持模块区和 vmalloc 区（arch/arm/mm/pageattr.c:66–68），不能就地释放 RO_DATA 中的页；”
  - 在“风险”中追加：“`kernel/bpf/sysfs_btf.c` 和 `btf_parse_vmlinux()` 直接引用 `__start_BTF`，都要改为指向副本；`.BTF_ids` 只保存类型编号，不受影响。”
- 需要增加的测试：
  - 确认 free_initmem 之后的“Freeing unused kernel memory”增加约 6.3 MiB；
  - 对 `/sys/kernel/btf/vmlinux` 的内容做哈希，与构建产物一致；
  - 在 free_initmem 之后加载带 BTF 的模块。

**R7.9-1【建议】先用 KSM 量出重复上界，再决定是否自建共享机制**：见 B3。在测量镜像上对选定的进程开启 KSM，读 `general_profit`，就能得到跨进程的真实重复量（包括已经驻留和换出后又换入的页），比自己写页哈希工具便宜。

## 二、对第 8 节问题的逐条答复

**问题 0：1.4 的副作用表是否完整？对开机时间的影响如何？还有哪些方案没有列出？**

不完整，见 R1.4-1：

- 布局噪声；
- LZ4 补丁影响整个文件系统的解压；
- vmalloc= 和 VMSPLIT 会使水位重算、ASLR 熵下降；
- 模块化带来 iTLB 成本，开机时还可能自动加载；
- btrfs-progs 的 udev 规则可能在开机时自动加载 btrfs 模块；
- TRIM_UNUSED_KSYMS 的构建成本；
- 关闭 KALLSYMS_ALL 的诊断后果。

开机时间这一项，测量方法本身有问题：在 `loglevel=4` 下，串口上没有内核标记可以用来分段（R4.6-1）。此外，冷函数候选无法排除开机阶段执行过的函数（R3.7-1）。

**问题 1：1.2、1.3 的口径是否正确、可执行？**

- 物理占用与容量估计分开、非 CMA 低端内存空闲低谷、修正 allocstall 的名称，这三点是正确的。
- 需要修改四处：
  - “总量 − 空闲”在压力场景下无效，在无压力场景下会被页缓存污染，应改为“不可回收占用（无压力场景）”加“容量指标（压力场景）”（R1.2-1）；
  - ARM32 上 kretprobe 拿不到 gfp 和 order，改用 `kmem/mm_page_alloc` 并按 `pfn == -1` 过滤，同时剔除试探性失败（R1.2-2）；
  - 多终点合取后整体检出力不足，需要按终点数提高单终点检出力（R1.3-1）；
  - `cycles/cpu-clock` 算出的不是频率，应改为绑核校准循环（R1.3-2）。
- p99 需要规定最少事件数（R1.3-3）。

**问题 2：2.3 和 3.3 是否正确？是否有遗漏的副作用？**

2.3 的数值、名义值与实际值的区分都正确。补充几点：

- SWIOTLB 池位于低端内存（`swiotlb.c:334`），并且要先确认存储 I/O 是否经过回弹（R2.3-1）；
- 3.3.1 漏了 kswapd 平衡判断的副作用（R3.3.1-1）；
- vmalloc= 的上界是 RAM 第一段的末尾 948 MiB，最多多出约 180 MiB，并且会使水位重算（R3.3.2-1）；
- SLUB 的 cache 合并会让单个 cache 的调整波及整个合并组（R3.3.5-1）；
- 3.2 中“模块化只在不加载时省内存”对低端内存不成立（R3.2-2），这也会影响 3.3 的整体排序。

**问题 3：3.1.1 的编译器条件、内核探测，以及 3.1.4 的限制分析是否成立？**

- 3.1.1 的条件 `arm && Linux && -meabi gnu` 正确，与 `Targets/ARM.cpp:326-330` 的 mcount 选择一致；内核探测带 `-meabi gnu` 也正确。只需在验证中补一条负例（R3.1.1-1）。
- 3.1.4 中关于 mcount 保留根、分段参数只作用于内建对象、`.text.unlikely` 被吞的分析都成立；但 `.text.hot` 不会被吞。0043ecea2399 已核实可以单独回移植（R3.1.4-1）。

**问题 4：3.7 用 function profiler 的精确调用次数确定冷函数、不用 `-fprofile-sample-accurate` 是否可靠？**

方向正确，“没采到不等于冷”的原则也写对了。剩下的缺口是开机覆盖：function profiler 只能在开机后打开（R3.7-1）。更好的做法是 C2 的首次执行位图：它能覆盖开机过程和关中断区间，开销比 function profiler 低得多，覆盖的函数也不限于 ftrace 能插桩的那些。

**问题 5：3.4.4 的设备级轮次管理和 3.6.1 的异步归还协议是否完整？**

- 3.4.4 是完整的：单一管理者、轮次合并、批量提交、前台事件中止，以及标记前后的验证项都齐了。
- 3.6.1 还缺两点：归还工作的 CPU 隔离和启动时机（推迟到前台首帧之后），以及与冻结的先后顺序（R3.6.1-1）。

**问题 6：第 5 节的阶段依赖和第 7 章的方案是否站得住？**

- 0a 和 0b 有循环依赖（R5-1）。
- 第 7 章中，7.8 在 ARM32 上只能通过 init 区实现（R7.8-1）；7.9 建议先用 KSM 测出重复上界（R7.9-1、B3）。其余各项的设计和最小实验都能成立。7.7 的“驱动和 subtarget 分离调度 CPU”方案与 `Arch/ARM.cpp` 的现状一致。

| A3 | 4.6 开机分段 | 用 ARM 通用定时器计数器作为跨固件、引导加载器、内核、用户态的统一时间轴 | `loglevel=4` 下串口没有内核标记；计数器从 SoC 上电起计数，不依赖修改启动参数（R4.6-1） |
| A4 | 1.3 A/A | 加入“布局扰动”的同功能构建，测出布局噪声 | 2% 的门槛与布局噪声处于同一量级，否则无法区分方案的效果和布局巧合（R1.4-1） |
| A5 | 3.2 模块化 | 按“低端内存收益（加载后同样成立）+ iTLB 成本 + 开机加载”重新评估每个候选，F2FS、cfg80211、Bluetooth 等必需但非热点的子系统也纳入候选 | 本平台的模块内存来自 HighMem，原文的判断低估了模块化对低端内存的价值（R3.2-2，C1） |

### B. 有依据的新方案

**B1. HZ 从 100 改为 250**

- 做什么：`CONFIG_HZ_250=y`。
- 依据：
  - ARM 的 HZ 是一个没有显式默认值的 choice（05 §1），本平台选的是 100。
  - 6.12 的 EEVDF 调度器在时钟中断中检查时间片是否用完。HZ=100 时，一个持续占用 CPU 的任务在时间片到期后，最多还能再运行约 10 ms 才被抢占（被唤醒时触发的抢占除外）。schedutil 的利用率更新也依赖时钟中断，升频的反应会变慢。
  - Android GKI 的 arm64 配置使用 HZ=250（公开配置；本次评审未逐行核对，标为无法核实）。
- 本平台的预期收益（推理）：后台 CPU 密集时，前台 UI 线程等待 CPU 的长尾从最多约 10 ms 缩短到约 4 ms；schedutil 升频更快。对切换耗时 p99 可能有可测的改善，幅度需要实测。
- 前提：NO_HZ_IDLE=y（平台配置已启用），空闲时没有额外的时钟中断。
- 风险：忙碌时时钟中断增加 2.5 倍，吞吐类指标可能下降不到 1%（估算）；jiffies 精度改变，用户态对此敏感的程序需要检查。
- 验证：切换耗时和冷启动的 p99、调度延迟（wakeup_rt）、吞吐类指标、开机时间。
- 阶段：3（与编译器类对照分开，单独一个变体）。

**B2. 抢占模型从 PREEMPT_VOLUNTARY 改为 PREEMPT（full）**

- 依据：
  - ARM32 支持 PREEMPT；PREEMPT_DYNAMIC 不能用，因为 ARM32 没有相应的架构选择（05 §1）。
  - Android GKI 使用 CONFIG_PREEMPT=y（公开配置；无法核实具体版本）。
  - v3 已经发现 mark_idle 的不可抢占区间问题（3.4.4），这类问题在 PREEMPT 下会自然消失。
- 本平台的预期收益（推理）：内核态的长循环（zram 标记和重压缩、slab 收缩、回收）不再阻塞前台线程，切换和交互的 p99 可能改善。
- 前提和风险：
  - 自旋锁与抢占计数的开销会使内核吞吐下降，常见的估计是 1%–2%（估算），可能超过 2% 的门槛；
  - 驱动中隐藏的抢占假设可能暴露出来。
- 验证：p99 类指标、吞吐类指标，以及 instructions:k 和 cycles:k；开启 DEBUG_PREEMPT 的诊断构建跑一遍完整场景。
- 阶段：3。与 B1 分别做对照，再做组合。

**B3. 按进程启用 KSM，先作为 7.9 的测量工具，再作为候选方案**

- 依据：
  - 上游已有按进程启用 KSM 的 `prctl(PR_SET_MEMORY_MERGE)`（6.4，本树 `kernel/sys.c:2777`）；
  - 按净收益统计的 `general_profit`（6.6，`mm/ksm.c:3669-3677`）；
  - 控制扫描 CPU 的 advisor（`mm/ksm.c:305-311`）。
  - 平台配置中 KSM 未设置但可以选择。
- 本平台的预期收益：取决于 TV 应用之间的重复率（例如多个 .NET 或 Web 运行时实例）。如果 general_profit 能达到数十 MiB，全机占用可以下降相应数量；否则为零。
- 风险：
  - 每个被扫描的页需要一个 `ksm_rmap_item`（`mm/ksm.c:202` 起），在 ARM32 上约 36–40 B，**位于低端内存的 slab 中**。扫描 400 MiB 匿名内存约需 4 MB 低端内存（估算），这正是本平台最紧的资源；
  - 扫描会占用 CPU；
  - 合并后的页在写时需要复制。
- 验证：
  - 测量镜像上只对 3–5 个候选进程开启 KSM，读取 `general_profit`、`pages_sharing`，以及 ksm_rmap_item 的 slab 大小，计算净收益（全机节省减去低端内存成本）；
  - 再用切换耗时和 CPU 评估是否值得作为正式方案。
- 阶段：2，作为 7.9 的前置测量。

### C. 探索性方案（第 7 章没有的）

**C1. 把“必需但不热”的子系统改为开机加载的模块，把它们从低端内存搬到 HighMem**

- 问题：低端内存是本平台最紧的资源，而内核映像中有大量必须保留、但不在热路径上的代码，例如 cfg80211、Bluetooth 协议栈、netfilter 的部分模块、F2FS（只用于 /opt/usr）。配置裁剪只能处理“可以不要”的功能；7.8 只针对 BTF 一项。
- 设计：
  - 用 function profiler 或 C2 的执行计数，选出调用频率低、体积大的必需子系统，改为模块，由开机流程按需加载；
  - 模块内存经 execmem 和 vmalloc 来自 HighMem（R3.2-2）；
  - ARM_MODULE_PLTS=y 已启用，模块区放不下时可以溢出到 vmalloc 区；
  - 不改内核机制，只改配置和开机加载顺序。
- 收益粗估：06 中这类子系统的对象大小量级为：net/bluetooth 约 0.52 MB、net/wireless 约 0.60 MB、net/mac80211 约 0.71 MB（mac80211 是否被本平台的 brcmfmac 使用需要确认）、fs/f2fs 约 0.53 MB。如果选出合计约 2 MB 的代码，低端内存可增加约 2 MB；全机占用增加几十 KB（页取整）。
- 风险：
  - 热点判断错误时，iTLB 缺失会拖慢性能；
  - 开机加载可能拉长开机时间；
  - F2FS 一类的子系统涉及挂载顺序（/usr/lib/modules 本身也是一个挂载点），需要放进 initramfs，或保证模块分区先挂载。
- 最小验证实验：只把 Bluetooth 改为模块（板上已加载 hci_uart 和 btbcm 模块，而 net/bluetooth 核心仍是内建的），开机后确认模块已加载、模块页位于 HighMem，比较非 CMA 低端内存的空闲量、开机时间和蓝牙配对或传输的延迟。

**C2. 用 SanitizerCoverage 的“首次执行位图”训练内核，取代 function profiler 确定冷函数**

- 问题：function profiler 不能覆盖开机阶段（R3.7-1）；它只能统计 ftrace 能插桩的函数；每次调用都要做一次哈希查找，开销大，会扰动训练场景。
- 设计：
  - 训练内核用 Clang 的 `-fsanitize-coverage=func,inline-bool-flag,pc-table` 编译。每个函数入口有一个 1 字节的标志，第一次执行时置 1，此后不再写入；pc-table 把标志映射回函数地址。
  - 沿用 KCOV 的 `KCOV_INSTRUMENT := n` 排除规则，避免插桩 noinstr 等敏感路径；
  - 增加约百行的训练专用补丁，用 debugfs 导出标志区和 pc-table；
  - 内核一启动就开始记录，开机、关中断区间和 notrace 以外的所有函数都能覆盖。
  - 冷函数清单 = 多个场景加开机过程中都没有置位的函数，交给 7.12 的编译器选项使用。
- 收益粗估：对体积本身没有直接收益，但让冷函数清单准确、能覆盖开机过程。训练开销估计为每次函数调用多一次读和条件分支（首次之后不再写入），远低于 function profiler，因此训练场景更接近真实行为。
- 风险：
  - Clang 对 ARM32 内核使用这种插桩的组合是否可用，需要实测（KCOV 在本平台未启用）；
  - 插桩会改变代码布局，训练内核不能用于性能验收；
  - 被内联的函数没有独立的标志。
- 最小验证实验：只对一个目录（例如 `net/bluetooth`）加上上述编译参数，开机后从 debugfs 读出位图，与该目录的 function profiler 结果对比；再确认一个开机时只执行一次的 probe 函数被正确置位。

**C3. 把 kallsyms 表和 BTF 一起移到 init 区，开机后转存到 HighMem**（对 7.8 的实质扩展）

- 问题：除了 BTF 之外，kallsyms 的几张表（`kallsyms_names` 1,841,884 B、`kallsyms_offsets` 507,072 B、`kallsyms_seqs_of_names` 380,304 B，合计约 2.73 MB，06 §2 中的 LLVM 普通版）也常驻在低端内存的只读区里。它们只在 oops、perf 符号解析、`/proc/kallsyms`、kprobe 注册时才会被访问。
- 设计：
  - 按 R7.8-1 的方式把这些表放进 init 区，在 free_initmem 之前复制到 vmalloc，并改用副本的指针；
  - kallsyms 的查找函数都通过这几个符号访问表，修改点相对集中；
  - 复制前（开机早期）出现的 oops 仍然使用原表。
- 收益粗估：低端内存约 2.7 MB 移到 HighMem，与 7.8 合计约 9 MB；全机占用基本不变（只多一份映射）。
- 风险：
  - kallsyms 的表由 link-vmlinux.sh 多遍链接生成，移动段的位置会影响多遍链接是否收敛；
  - panic 和 oops 路径中会访问 vmalloc 映射，需要确认此时映射一定存在（开机后一直存在）；
  - 与 KALLSYMS_ALL 的裁剪（3.2）有重叠：如果先关闭 KALLSYMS_ALL，这里的收益约减半。
- 最小验证实验：先只移动 `kallsyms_names` 一张表，确认多遍链接能收敛、开机后 `/proc/kallsyms` 的内容一致、free_initmem 释放的量增加了相应大小，然后再扩展到全部表和 BTF。

## 四、总结

**最重要的 5 个问题**

1. **R1.2-1【重要】** “全机物理占用 = 总量 − 空闲”在压力场景下贴着水位线、测不出变化，在无压力场景下又被页缓存污染。应改为“不可回收占用（无压力场景）”加“容量指标（压力场景）”两类门槛。
2. **R4.6-1【重要】** 本镜像的启动参数是 `loglevel=4`，串口上没有内核日志可以用来分段，zImage 解压器也没有输出（DEBUG_LL 未设置）。开机分段需要改用 ARM 通用定时器计数器或引导加载器的输出。
3. **R1.3-1 / R1.3-2【重要】** 多个终点合取后整体检出力很低，按现有轮次一个中性变体也很难通过；`cycles/cpu-clock` 算出的是利用率乘以频率，会把正常轮次误判为降频而作废。
4. **R1.2-2【重要】** ARM32 不支持 `$argN`，kretprobe 拿不到 gfp 和 order；`kmem/mm_page_alloc` 在分配失败时也会触发（pfn=-1），可以直接使用，但要剔除试探性的失败。
5. **R3.2-2 / R7.8-1 / R3.7-1【重要】**
   - 模块内存在本平台来自 HighMem，所以模块化加载后低端内存收益依然存在，原文低估了它；
   - ARM32 不能在线性映射区按页释放只读数据，7.8 必须把 BTF 放进 init 区；
   - function profiler 覆盖不了开机过程，“开机执行过的函数不当作冷函数”这一要求无法满足。

**B 类前 3**

1. B3：按进程启用 KSM，先作为测量工具，注意 rmap_item 位于低端内存；
2. B1：HZ=250，改善 EEVDF 的时间片执行和 schedutil 的响应；
3. B2：抢占模型改为 PREEMPT。

**C 类前 3**

1. C1：把必需但不热的子系统改为模块，把它们从低端内存搬到 HighMem；
2. C2：首次执行位图训练内核；
3. C3：kallsyms 表与 BTF 一起转存到 HighMem。

**总体结论：修改后冻结。** v3 采纳了上一轮的绝大部分意见，3.1.1 的编译器条件、低端内存的名义值与实际值、zram 的设备级轮次、3.7 不再把“没采到”当作冷，这些都已经正确。剩下的问题集中在测量口径和测量方法的可执行性上：物理占用指标、开机分段、检出力、频率校验、分配失败的计数方式。另外有三处平台事实需要修正：模块内存来自 HighMem、ARM32 rodata 不能按页释放、function profiler 覆盖不了开机过程。这些都是局部修改，改完即可冻结。
